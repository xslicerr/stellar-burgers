# Стартер на TypeScript для проекта Stellar Burger

## Запуск

1. Установите зависимости: `npm ci`.
2. Скопируйте `.env.example` в `.env`. Рабочее значение: `BURGER_API_URL=https://norma.ffapi.ru/api`.
3. Запустите `npm start` и откройте [http://localhost:4000](http://localhost:4000).

После изменения `.env` перезапустите сервер. Каталог и публичная лента доступны без входа. История и профиль требуют авторизации. Лента и история автоматически обновляются через REST каждые пять секунд; после создания заказа обновляются сразу.

## Проверки

```bash
npx tsc -p tsconfig.app.json --noEmit
npm run check
npm test -- --runInBand
npm run test:coverage
npm run build
```

Браузерные тесты используют подмену API и не создают реальные аккаунты или заказы:

```bash
npx playwright install chromium
npm run e2e -- --workers=2
```

## Тесты проектной работы

`tests/constructor.pl.tsx` проверяет добавление и замену булок, добавление начинок,
удаление и перестановку ингредиентов, открытие окна ингредиента и закрытие
крестиком, Escape и кликом по оверлею. Отдельный сценарий подставляет тестовые
access- и refresh-токены, собирает бургер, проверяет состав и авторизацию запроса
заказа, номер в модальном окне, пустой конструктор и закрытие окна.

Сценарии сгруппированы в `test.describe`: ингредиенты, конструктор, оформление
заказа, авторизация и профиль, лента и история, маршрутизация. Проверки модалки
разделены на независимые тесты. Открывается «Лунный сыр» (`main-2`, четвёртая
запись HAR): проверяются название, изображение и каждый показатель пищевой
ценности. Картинки и пищевая ценность разных ингредиентов различаются.
Оверлей выбирается через `getByTestId('modal-overlay')`; клик задаётся относительно
оверлея, а не абсолютной координатой страницы.

**Все ответы бэкенда воспроизводятся через `page.routeFromHAR`:**

- `tests/fixtures/ingredients.har` — пять вымышленных ингредиентов со встроенными
  SVG-картинками.
- `tests/fixtures/api.har` — вход, регистрация, проверка пользователя, обновление
  токена, выход, восстановление пароля, создание заказа, лента, история и детали.
- `tests/fixtures/scenarios/*.har` — сохранённый профиль, созданный заказ,
  заказ с соусом, зарегистрированный пользователь, изменение статуса, несколько
  заказов и ошибки API.

Общая автоматическая фикстура `tests/helpers/api.ts` подключает HAR до перехода
на страницу. Сценарии меняют только нужные ответы, остальные находятся в базовых
HAR. В конце цепочки стоит `notFound: 'abort'`: неизвестный запрос не уходит
в реальный бэкенд и приводит к ошибке теста. Ответы вручную через `route.fulfill`
не формируются. Playwright сам запускает Vite с тестовым адресом API.

HAR и JSON для ожидаемых значений можно заново создать командой
`node tests/fixtures/generate-hars.mjs`. Генератор использует только вымышленные
данные и не обращается в сеть. При обычном запуске тестов готовые HAR только
читаются (`update: false`). Реальные заказы и аккаунты не создаются.

Юнит-тесты расположены рядом со слайсами:

- `ingredients-slice.test.ts`: начальное состояние при `UNKNOWN`, сохранение
  состояния при неизвестном экшене, `pending`, `fulfilled`, `rejected`, пустой
  ответ сервера и ошибка без сообщения.
- `constructor-slice.test.ts`: начальное состояние при `UNKNOWN`, все четыре
  экшена конструктора, уникальные id повторяющихся ингредиентов, замена булки,
  добавление соуса, перестановка в обе стороны и некорректные индексы. Проверка
  отрицательной целевой позиции использует три начинки и булку: ошибочное
  поведение `splice` больше не может случайно сохранить тот же порядок.
- `store.test.ts`: взаимодействие слайсов при загрузке ингредиентов и создании
  заказа, повторные запросы и обработка запоздавших ответов.

`npm run test:coverage` выводит покрытие двух обязательных слайсов в терминал
и создаёт HTML-отчёт `coverage/index.html` и `coverage/lcov.info`.
Проценты относятся к этим слайсам, а не ко всему приложению.
Настройки отчёта описаны в [документации Jest](https://jestjs.io/docs/configuration#collectcoverage-boolean),
воспроизведение HAR — в [документации Playwright](https://playwright.dev/docs/mock#replaying-from-har).

Проверить типы приложения и обоих наборов тестов можно отдельно:

```bash
npx tsc -p tsconfig.app.json --noEmit
npx tsc -p tsconfig.test.json --noEmit
npx tsc -p tsconfig.e2e.json --noEmit
```

В Windows можно использовать уже установленный Edge без скачивания Chromium. В PowerShell:

```powershell
$env:E2E_BROWSER_CHANNEL = 'msedge'
npm run e2e -- --workers=2
```

## Процедура создания коммита с проверками

При создании коммита автоматически запускаются проверка линтерами `stylelint`, `eslint` и форматирование `prettier`.

Если линтер обнаружит ошибки:

- Коммит создан не будет
- Необходимо исправить все выявленные проблемы
- Добавить исправленные файлы в индекс: `git add .`
- Повторить коммит

**Рекомендация:**  
Для предотвращения ошибок на этапе коммита предварительно выполните:  
`npm run lint`. Это позволит выявить и исправить проблемы до создания коммита.

Есть также команды для запуска проверок по отдельности:

- `npm run eslint` - запускает проверку линтера и исправляет проблемы, которые можно исправить автоматически,
- `npm run stylelint` - запускает проверку литера для файлов стилей и исправляет проблемы, которые можно исправить автоматически,
- `npm run prettier` - исправляет ошибки форматирования кода.

Можно добавить автозапуск этих команд при сохранении файла в вашей IDE.

Для создания коммита рекомендуется запускать команду `npm run commit`. Она позволяет обеспечить соответствие описаний коммитов [общепринятым соглашениям](https://www.conventionalcommits.org/en/v1.0.0/).

В проекте настроены алиасы, которые можно использовать при импорте модулей:

```
	alias: {
		'@': path.resolve(__dirname, './src'),
		'@components': path.resolve(__dirname, './src/components'),
		'@services': path.resolve(__dirname, './src/utils'),
		'@pages': path.resolve(__dirname, './src/pages'),
		'@utils': path.resolve(__dirname, './src/utils'),
	},
```
